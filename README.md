# Система учета материалов ИП

## Актуальный этап: ПР10

Ветка `pr10-django-admin` создана от ПР9; main не изменяется.
Установка: `python -m pip install -r requirements.txt`, затем
`python manage.py migrate`. Для пустой ORM-базы: `python manage.py import_pr7`.
После переноса создайте личную учётную запись командой
`python manage.py createsuperuser`. Пароли и db.sqlite3 не включаются в Git.
Запуск: `python manage.py runserver`, административная панель: `/admin/`.

### Административная панель

Зарегистрированы Material и Operation, локализованы приложения, модели и поля.
Списки имеют столбцы, поиск, фильтры, сортировку и постраничный вывод.
В карточке материала видна история через read-only TabularInline.
Операция создаётся через record_operation(), отменяется через cancel_operation().
Редактировать количество, дату, вид и материал существующего движения нельзя;
удаление истории отключено. Можно менять примечание и допустимый статус.
Действие отмены также вызывает сервис, а не массовый update().
Недостаточный остаток и повторная активация отменённой записи отклоняются.
Материал с историей защищён ForeignKey(PROTECT). Изменение складского остатка
в карточке материала доступно администратору как ручная корректировка:
это не новое движение и не автоматическая сверка истории.

### Статусы и миграция данных

Operation.Status(TextChoices): ACTIVE, CANCELLED, COMPLETED. Сначала миграция
0003 добавляет status, затем RunPython переносит cancelled=True в CANCELLED,
остальные записи в ACTIVE, и лишь после этого удаляет BooleanField.
Совместимое Python-свойство cancelled оставлено для старых потребителей,
но ORM-фильтры и шаблоны используют status. Команда импорта ПР7 тоже преобразует
старый формат. Менеджер QuerySet предоставляет active(), cancelled(),
completed(), for_date(), effective(); методы используются веб-запросами.

В отличие от бронирований, завершённое складское движение уже изменило запас:
COMPLETED, как и ACTIVE, входит в оборот и подбор без расхода на дату.
Только CANCELLED исключается из этих расчётов. Число записей каждого статуса
показывается отдельно на странице статистики. Даты сами не завершают операции.

### Slug и вычисляемые данные

Material.slug уникален; прежним материалам назначены material-<id> миграцией.
Новые записи получают уникальный UUID по умолчанию, код можно изменить в admin.
get_absolute_url() возвращает `/materials/item/<slug>/`, по нему работают ссылки
каталога и View on site в админке. Старые числовые URL сохранены.
stock_value — GeneratedField(price * quantity, db_persist=True): значение
пересчитывается SQLite, для чтения после save() нужен refresh_from_db().
Контекстный процессор inventory_context выводит название и количество материалов
в общей навигации; это один дополнительный COUNT-запрос на страницу.

### SQL и Django Debug Toolbar

Пакет django-debug-toolbar подключён только при DEBUG=True и вне pytest.
INTERNAL_IPS ограничены localhost; маршруты `/__debug__/` отсутствуют при DEBUG=False.
Откройте список, карточку операции и страницу с фильтром, затем вкладку SQL.
Список использует annotate(F(...)).values(...), поэтому связанные данные
получаются одним JOIN без создания связанных объектов. Подробная страница
использует select_related('material'). В тестовом примере с пятью операциями
наивный доступ к material.name делает 6 запросов, оптимизированный список — 1,
подробная запись вместе с материалом — 1. Дополнительные COUNT пагинатора,
контекстного процессора и запросы авторизации не являются N+1.

## Управление складом через сайт

В ПР9 и ПР10 добавлены пользовательские формы, а не только страницы просмотра.
Нажмите «Войти» и войдите учётной записью с разрешениями на соответствующие
модели. Для локальной демонстрации можно создать суперпользователя:
`.\.venv\Scripts\python.exe manage.py createsuperuser`.
Без входа сайт доступен для чтения; изменение требует прав Django.

- `/materials/new/`: создание материала с начальным остатком;
- `/materials/<id>/edit/`: изменение названия, категории, цены и единицы;
- `/materials/<id>/delete/`: подтверждение удаления материала без истории;
- `/operations/new/`: поступление или расход с выбором материала и даты;
- `/operations/<id>/edit/`: изменение только примечания;
- `/operations/<id>/cancel/`: подтверждение отмены с восстановлением остатка.

Действия доступны кнопками в списках и карточках. Изменения выполняются только
POST-запросами с CSRF; GET на удаление или отмену лишь показывает подтверждение.
Остаток не редактируется в форме материала. Единица материала с историей
заблокирована. Перерасход, повторная отмена и отмена израсходованного поступления
запрещены. История не удаляется. Ошибки показываются в форме, успех — после
перехода. Операции используют атомарные сервисы. Запись ведётся в ORM-базу
ветки; исходные JSON и SQLite ПР7 не меняются.

Реализация: `materials_web/forms.py`, `materials_web/actions.py`,
`operations_web/forms.py`, `operations_web/actions.py`, общие шаблоны форм.
Проверки пользовательских сценариев: `tests/test_workflows.py`.


После запуска: http://127.0.0.1:8000/.

### Модели и стратегия переноса

`materials_web/models.py`: Material (name, price, quantity, unit, category).
`operations_web/models.py`: Operation (material, kind, quantity, date, note,
cancelled). Django создаёт первичные ключи автоматически. ForeignKey material
использует PROTECT и related_name='operations': материал с историей удалить
нельзя, а история доступна через material.operations.all(). Дата имеет тип
DateField, отмена BooleanField, необязательное примечание TextField с blank/null.
CheckConstraint и валидаторы проверяют допустимые количества и виды операций.

Выбрана стратегия новой управляемой базы: исходный `data/materials.sqlite`
остаётся неизменным источником ПР7. Миграции создают таблицы в локальном
`db.sqlite3`, который исключён из Git. Команда import_pr7 читает старую базу
в режиме read-only, проверяет данные, переносит материалы перед операциями
и сохраняет исходные ID и ForeignKey. Перенос выполняется атомарно;
повторный запуск без --replace не удаляет существующие данные.
Прямой sqlite3 допустим только в этой команде переноса и архивном слое ПР7.

### ORM и пользовательские сценарии

Все прежние адреса сохранены. `db/orm_queries.py` реализует 16 отдельных
запросов: списки и карточки, поиск материалов по имени/остатку, фильтры
операций, подбор без действующего расхода на дату, сводки, категории,
активность, последние операции и материалы без истории. Используются
all/filter/exclude/get, values/values_list, select_related, aggregate,
annotate, Count/Sum/Min/Max/Avg, условные Q и срез [:5]. Поиск журнала
дополнительно использует Q по имени связанного материала или примечанию.
Минимум ПР9: 15 различных ORM-выражений; минимум по категориям соблюдён.

Журнал `/operations/` поддерживает q, kind, state, date, sort и page.
sort принимает только newest, oldest, material: сортировка по дате, по дате
и ID либо по имени связанного материала. Paginator выдаёт 10 записей;
querystring в шаблоне сохраняет фильтры и сортировку в ссылках перехода.
Некорректный номер страницы обрабатывается get_page(), неизвестный sort
возвращает 400. Отсутствующий объект получает 404.

`operations_web/services.py` предоставляет атомарные record_operation() и
cancel_operation(): отрицательный остаток, повторная отмена и отмена уже
израсходованного поступления запрещены. CRUD демонстрируется через shell
и тесты, новые публичные формы редактирования не вводились.

```python
from materials_web.models import Material
from operations_web.services import record_operation, cancel_operation
m = Material.objects.create(name='Тест', price=10, quantity=5,
                            unit='шт', category='Тест')
op = record_operation(m.pk, 'expense', 2, '2026-11-08')
cancel_operation(op.pk)
op.delete()
m.name = 'Обновлено'
m.save()
m.delete()
```

## Веб-интерфейс ПР7

Веб-часть получает данные из `data/materials.sqlite` через стандартный модуль
`sqlite3`. Представления вызывают именованные запросы из `sql/queries.sql`,
получают `sqlite3.Row` и передают результаты в шаблоны через `render()`.
JSON во время HTTP-запросов не читается. HTML не формируется в Python.
Django ORM и Django Forms для предметных данных не используются; фильтры
реализованы обычными HTML-формами GET с серверной проверкой параметров.

Общая структура находится в `templates/base.html`, навигация вынесена в
`templates/includes/navigation.html`. Дочерние страницы применяют `extends`,
`block` и `include`, а списки, состояния и пустые коллекции отображаются через
`for`, `if` и `empty`. Ссылки строятся по именованным URL с пространствами имён.
Для представления значений используются фильтры `length`, `default` и
`floatformat`.

Собственная статика хранится в `homepage/static/homepage/`: CSS оформляет
интерфейс, SVG используется как логотип, а JavaScript выводит текущий год в
подвале. Bootstrap сохранён как вспомогательная библиотека.

| Страница | URL | Назначение |
| --- | --- | --- |
| Главная | `/` | описание проекта и сводка запасов |
| Материалы | `/materials/` | список SQLite; поиск `?q=Краска&quantity=1` |
| Материал | `/materials/<id>/` | карточка материала или ответ HTTP 404 |
| Операции | `/operations/` | история; фильтры `state`, `kind`, `date` |
| Операция | `/operations/<id>/` | карточка операции или ответ HTTP 404 |
| Подбор | `/materials/available/` | текущий запас и отсутствие расхода на дату |
| Статистика | `/statistics/` | сводки, категории, активность `?threshold=1` |

Маршруты распределены по Django-приложениям `homepage`, `materials_web` и
`operations_web`. Имена веб-приложений не совпадают с именами модулей
`materials.py` и `operations.py`, поэтому консольная часть продолжает работать
без изменения импортов.

| Представление | Назначение |
| --- | --- |
| `homepage.views.index()` | Главная страница и статистика |
| `homepage.views.page_not_found()` | Общая страница HTTP 404 через шаблон |
| `homepage.views.statistics()` | Агрегаты, GROUP BY и HAVING |
| `materials_web.views.materials()` | Список материалов |
| `materials_web.views.material_detail()` | Поиск и карточка материала |
| `materials_web.views.available()` | Подбор запасов, подзапрос NOT EXISTS |
| `operations_web.views.operations()` | История операций |
| `operations_web.views.operation_detail()` | Поиск и карточка операции |

В веб-части поиск по ID выполняется SQL-запросами `material_detail` и
`operation_detail`. `fetch_one()` возвращает строку или `None`; представление
проверяет результат до использования полей. Функции поиска объектов из ПР5
сохранены для консольной реализации и её тестов.

### Сценарии поиска

На странице материалов поиск использует LIKE с параметром: `%` и `_` из
пользовательского ввода экранируются как обычные символы. Поиск кириллицы
учитывает регистр (стандартное поведение SQLite LIKE без расширений).
Количество должно быть конечным неотрицательным числом.

В журнале `state=active` показывает действующие операции, `state=cancelled`
показывает отменённые; `kind=receipt` означает поступления, `kind=expense`
означает расходы. Дата передаётся в формате `YYYY-MM-DD`. Условия можно
комбинировать. Ошибочные параметры возвращают страницу с сообщением и HTTP
400, отсутствие подходящих записей является обычным результатом HTTP 200.

Подбор без даты показывает материалы с положительным текущим остатком.
При выборе даты дополнительно исключаются материалы, имеющие действующий
расход в этот день. Отменённый расход не исключает материал. Это аналог
поиска по дате из методички, адаптированный к складу: исторический остаток
не восстанавливается, резервирование не выполняется. Значения количества
сравниваются в единице соответствующего материала.

Статистика не суммирует литры с килограммами: движение группируется по
материалу и его единице. Денежные показатели операций рассчитываются по
текущей цене материала, поскольку историческая цена в исходной модели
отсутствует. Отменённые операции не входят в оборот и активность.

## SQLite и SQL: ПР7

Файл `data/materials.sqlite` включён в результат практики. Он отделён от
служебной базы Django `db.sqlite3` (авторизация, сессии и admin). Создавать
модели Django и миграции для материалов и операций на ПР7 не требуется.

Схема находится в `sql/schema.sql`:

| Таблица | Поля и SQLite-типы |
| --- | --- |
| `materials` | `id INTEGER`, `name TEXT`, `price REAL`, `quantity REAL`, `unit TEXT`, `category TEXT` |
| `operations` | `id INTEGER`, `material_id INTEGER`, `kind TEXT`, `quantity REAL`, `date TEXT`, `note TEXT`, `cancelled INTEGER` |

В обеих таблицах `id` является PRIMARY KEY. Связь один-ко-многим:
`operations.material_id` ссылается на `materials.id`; удаление материала
с операциями запрещено. На каждом соединении включено
`PRAGMA foreign_keys = ON`. CHECK ограничивает количества, цены, вид операции,
дату и признак отмены (0 или 1). Обязательные поля имеют NOT NULL;
пустое примечание импортируется как SQL NULL и показывается через `default`.
Индекс `operations_material_date` поддерживает поиск движений материала.

`db/database.py` создаёт соединения и выполняет схему. Повторное создание
безопасно благодаря IF NOT EXISTS. `db/import_json.py` проверяет исходные
данные существующей предметной моделью, вставляет сначала материалы,
затем операции через executemany() и фиксирует всё одной транзакцией.
Ошибка вставки вызывает rollback(). Остатки копируются как готовый снимок:
поступления и расходы не применяются повторно. JSON не изменяется.

### Создание и импорт

```powershell
.\.venv\Scripts\python.exe -m db.database
.\.venv\Scripts\python.exe -m db.import_json
```

Импорт сам создаёт схему, поэтому первая команда необязательна. База уже

```powershell

```

Для независимого файла используйте `--database data/check.sqlite`, для другой
папки JSON — `--source PATH`. Веб-чтение открывает SQLite в режиме read-only;
неправильный путь не создаёт молча пустую базу. Соединения закрываются явно.
После изменений JSON нужна повторная явная загрузка: консоль и сайт не
синхронизируются автоматически на этом учебном этапе.

### Каталог запросов

В `sql/queries.sql` находятся 14 запросов с комментариями и метками
`-- name: ...`. `db/queries.py` читает этот же файл, а не хранит копии SQL.
Значения передаются отдельно через `?`, не подставляются в SQL f-строками.
Все 14 запросов используются веб-представлениями; это проверяет тест.

| № | Имя запроса | Назначение и страница |
| --- | --- | --- |
| 1 | `materials_list` | SELECT списка материалов: `/materials/` |
| 2 | `operations_list` | SELECT журнала и JOIN: `/operations/` |
| 3 | `materials_search` | WHERE по названию и остатку: `/materials/?q=Краска` |
| 4 | `materials_in_stock` | WHERE по текущему запасу: `/materials/available/` |
| 5 | `active_operations` | WHERE и JOIN: `/operations/?state=active` |
| 6 | `operations_filter` | Несколько WHERE-условий и JOIN: фильтры журнала |
| 7 | `materials_without_expense` | NOT EXISTS и дата: подбор без расхода |
| 8 | `stock_summary` | COUNT, DISTINCT, SUM: главная и статистика |
| 9 | `operation_summary` | COUNT и SUM с JOIN: главная и статистика |
| 10 | `category_statistics` | GROUP BY, COUNT, SUM, MIN, MAX, AVG: статистика |
| 11 | `material_activity` | LEFT JOIN и GROUP BY, включая нулевую активность |
| 12 | `frequent_materials` | GROUP BY и HAVING с порогом: статистика |
| 13 | `material_detail` | WHERE по ID и стоимость: карточка материала |
| 14 | `operation_detail` | JOIN и WHERE по ID: карточка операции |

Минимум методички соблюдён: не менее двух списков, WHERE, JOIN,
агрегатных запросов и GROUP BY. Один запрос может сочетать несколько видов.

### Два случая HTTP 404

Несуществующие объекты (`/materials/999/`, `/operations/999/`) получают
предметные сообщения «Материал не найден» и «Операция не найдена» со статусом
404 непосредственно из view. Это работает и при включенной отладке.

Неизвестные маршруты, например `/nonexistent/` или `/materials/abc/`,
обрабатывает `handler404 = 'homepage.views.page_not_found'`, объявленный
в корневом `inventory_web/urls.py`. Исключение `Http404` из view также
передается этому обработчику. Возврат готового ответа со статусом 404
повторно обработчик не вызывает.

Для демонстрации общей страницы установите `DEBUG = False` в
`inventory_web/settings.py`, запустите сервер и откройте `/nonexistent/`.
Разрешенные локальные хосты уже указаны в `ALLOWED_HOSTS`. После проверки
верните `DEBUG = True`: именно такой порядок предусмотрен ПР5.
При `DEBUG = True` для неизвестного маршрута Django показывает отладочную
страницу. Тесты проверяют оба режима через `override_settings`, без правки
рабочих настроек.

## Объектная модель

### `Material`

Материал на складе ИП. Атрибуты: `id`, `name`, `price`, `quantity`, `unit`,
`category`.

Основные методы:

- `calculate_cost()` - расчет стоимости количества;
- `is_available()` - проверка наличия;
- `remaining_after()` - расчет остатка без изменения объекта;
- `receive()` и `spend()` - изменение складского остатка;
- `from_data()` и `to_data()` - преобразование JSON-данных;
- `__str__()` - строковое представление материала.

### `Operation`

Поступление или расход материала. Атрибуты: `id`, `material`, `kind`,
`quantity`, `date`, `note`, `cancelled`.

Основные методы:

- `cancel()` - отмена операции и восстановление остатка;
- `from_data()` и `to_data()` - преобразование JSON-данных;
- `__str__()` - строковое представление операции.

`Operation` хранит ссылку на объект `Material`, а не только его идентификатор.
Это композиция объектов предметной области. При сохранении ссылка преобразуется
в `material_id`, а при загрузке восстанавливается по коллекции материалов.

Функции поиска, сортировки, фильтрации и статистики работают с коллекциями
объектов. Ввод, меню и файловые операции остались отдельными функциями, потому
что не относятся к поведению одного конкретного объекта.

Инкапсуляция проявляется в методах изменения остатка и отмены операции.
Полиморфизм демонстрирует единый вызов `str(object)` для `Material` и
`Operation`. Искусственное наследование не используется: операция не является
разновидностью материала, поэтому между сущностями применена композиция.

## Хранение данных

`data/materials.json` содержит массив данных материалов:

```json
[
  {
    "id": 1,
    "name": "Краска",
    "price": 500,
    "quantity": 8,
    "unit": "л",
    "category": "Отделка"
  }
]
```

`data/operations.json` содержит отдельный массив операций:

```json
[
  {
    "id": 1,
    "material_id": 1,
    "kind": "expense",
    "quantity": 2,
    "date": "2026-09-25",
    "note": "Кухня",
    "cancelled": false
  }
]
```

При запуске консоли или импорта JSON преобразуется в `list[Material]` и `list[Operation]`.
После загрузки `operation.material` ссылается на объект из коллекции материалов.
Перед сохранением объекты преобразуются в обычные структуры JSON. Поврежденный
файл не перезаписывается, запись выполняется через временные файлы.

## Правила операций

- название, единица и категория обязательны;
- цена и начальное количество неотрицательны;
- количество операции должно быть больше нуля;
- расход не может превышать остаток;
- повторная отмена запрещена;
- отмененное поступление нельзя применить, если материал уже израсходован;
- отмененные записи сохраняются в истории.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m flake8
```

Тесты проверяют создание объектов, методы и `__str__`, операции над
коллекциями, связь `Operation` с `Material`, отмену, JSON-преобразования,
ошибочный ввод, полный сценарий меню, Django-маршруты, содержимое страниц и
обработку несуществующих идентификаторов с кодом HTTP 404.
Также проверяются общий `handler404`, исключение `Http404`, недопустимые
параметры URL, именованные маршруты, навигация, пустые списки и экранирование
HTML. Тесты SQLite проверяют схему, ограничения, импорт, rollback, реальные
параметризованные запросы, фильтры, NULL, агрегаты, GROUP BY и HAVING.
Веб-тесты используют отдельную SQLite-базу в каждом тесте; рабочие JSON и
`data/materials.sqlite` не меняются. В `pytest.ini` указан игнорируемый
каталог `.pytest_work` непосредственно в корне: его первый запуск не зависит
от существования `.pytest_cache` и не требует доступа к общему Windows Temp.

ПР7 добавляет SQLite и самостоятельный SQL-слой без Django ORM. Сохранены
шаблоны и статика ПР6, прежние страницы получают данные из SQLite.
Добавлены поиск запасов, фильтрация журнала, подбор по дате и статистика.

относится к следующим практическим работам.

## Демонстрационный сценарий

1. Добавить материал: краска, 500 руб., 10 л, категория «Отделка».
2. Найти материал, отсортировать список и отобрать категорию.
